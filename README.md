# 🛡️ Security Triage Agent

**An AI agent that decides which vulnerability to fix first by reasoning over a knowledge graph, remembers what it concluded, opens tickets for the right team, and shows the exact path behind every answer.**

Built solo for **Graph Hacks: Context for AI Agents** (WeMakeDevs × FalkorDB) — **Track 01: Agents That Act on Connected Data**.

## The problem

Security teams get a flat list of CVEs sorted by CVSS score. But a score alone doesn't say **how much of your company is actually exposed**. A "9.8" buried in an internal tool can matter less than a "9.1" sitting underneath five public-facing services.

Answering "what should we fix first, and who do we tell?" means following connections:

`service → package → package → CVE`, `service → calls → service`, `team → owns → service`.

That is a graph problem, not a text-search problem.

## What the agent does

Ask it in plain English. It picks graph tools, follows multi-hop dependency chains, and answers with the evidence.

## Graph schema


(Team)-[:OWNS]->(Service)
(Service)-[:DEPENDS_ON]->(Package)-[:DEPENDS_ON]->(Package)
(Package)-[:HAS_VULN]->(CVE)
(Service)-[:CALLS]->(Service)

-- written by the agent --
(Case)-[:CONCERNS]->(CVE)
(Ticket)-[:ABOUT]->(CVE), (Ticket)-[:ABOUT_SERVICE]->(Service), (Ticket)-[:ASSIGNED_TO]->(Team)


## How it maps to Track 1

- **Multi-hop reasoning:** variable-length traversals (`DEPENDS_ON*1..4`) from services through packages to CVEs, and `CALLS*1..3` to find indirectly affected callers.
- **Graph queries as agent tools:** `prioritize_cves`, `blast_radius`, `find_owner`, `downstream_impact`, `explain_path`.
- **Actions based on what the graph shows:** `create_ticket` assigns work to the team the graph says owns the service.
- **Explainable results:** every tool returns its path, the UI lists each tool call, and the graph view highlights the path used.
- **Memory:** `save_case` and `recall_cases` persist findings in the graph so the agent remembers across sessions.

## Why the graph is essential

FalkorDB is the primary database and the product does not work without it: every agent tool is a graph query, the agent's memory (`Case`) and actions (`Ticket`) are nodes and edges connected to the CVEs, services and teams they concern, and ticket routing comes from the `(Team)-[:OWNS]->(Service)` relationship. The core questions need variable-length traversals across several hops, which is what the graph is for.

## Cypher queries the product depends on

**Blast radius of a CVE — multi-hop traversal** (`tools.py`, `blast_radius`)
```cypher
MATCH p=(s:Service)-[:DEPENDS_ON*1..4]->(:Package)-[:HAS_VULN]->(c:CVE {id:$id})
MATCH (t:Team)-[:OWNS]->(s)
RETURN s.name, s.criticality, s.public, t.name, t.oncall, length(p) AS hops,
       [n IN nodes(p) | coalesce(n.name, n.id)] AS path
ORDER BY hops
```

**Risk ranking input** (`tools.py`, `prioritize_cves`) — every (CVE, service) pair reachable through the dependency graph. Risk score = CVSS × Σ(service criticality × 2 if public-facing else 1), computed from these rows.
```cypher
MATCH (s:Service)-[:DEPENDS_ON*1..4]->(:Package)-[:HAS_VULN]->(c:CVE)
RETURN DISTINCT c.id, c.severity, c.cvss, s.name, s.criticality, s.public
```

**Indirect impact — who calls the affected service** (`tools.py`, `downstream_impact`)
```cypher
MATCH p=(caller:Service)-[:CALLS*1..3]->(s:Service {name:$n})
RETURN caller.name, caller.criticality, caller.public, length(p) AS hops,
       [n IN nodes(p) | n.name] AS path
ORDER BY hops
```

**Explain one exposure — shortest dependency path** (`tools.py`, `explain_path`)
```cypher
MATCH p=(s:Service {name:$s})-[:DEPENDS_ON*1..4]->(:Package)-[:HAS_VULN]->(c:CVE {id:$c})
RETURN [n IN nodes(p) | coalesce(n.name, n.id)] AS path, length(p) AS hops
ORDER BY hops LIMIT 1
```

**Ownership** (`tools.py`, `find_owner`)
```cypher
MATCH (t:Team)-[:OWNS]->(s:Service {name:$n}) RETURN t.name, t.oncall
```

**Action — open a ticket routed through the graph** (`memory_tools.py`, `create_ticket`)
```cypher
MATCH (t:Team)-[:OWNS]->(s:Service {name:$s}), (c:CVE {id:$c})
CREATE (k:Ticket {id:$id, summary:$sum, status:'open', created:$ts})
CREATE (k)-[:ABOUT]->(c)
CREATE (k)-[:ABOUT_SERVICE]->(s)
CREATE (k)-[:ASSIGNED_TO]->(t)
```

**Memory — save and recall investigations** (`memory_tools.py`, `save_case`, `recall_cases`)
```cypher
CREATE (:Case {id:$id, question:$q, conclusion:$c, created:$t})

MATCH (k:Case)-[:CONCERNS]->(c:CVE {id:$id})
RETURN k.id, k.question, k.conclusion, k.created
ORDER BY k.created DESC LIMIT 5
```

## Tech stack

## Run it yourself

**1. Clone and install**
```bash
git clone <your-repo-url>
cd graphhack-agent
python -m venv .venv
source .venv/bin/activate        # Windows PowerShell: .venv\Scripts\activate
pip install -r requirements.txt
```

**2. Get a FalkorDB instance** — either:
- FalkorDB Cloud (free tier): https://app.falkordb.cloud, or
- locally: `docker run -p 6379:6379 -p 3000:3000 falkordb/falkordb`

**3. Configure**
```bash
cp .env.example .env
# then fill in your FalkorDB host/port/user/password and your GEMINI_API_KEY
```
Leave the `FALKORDB_` values empty to use a local instance on `localhost:6379`.

**4. Build the graph and start the app**
```bash
python seed.py          # builds the synthetic security graph (re-running resets it)
streamlit run app.py
```

Test the tools without any LLM calls: `python tools.py` and `python memory_tools.py`.

## Project structure

```
seed.py          builds the synthetic graph in FalkorDB
tools.py         graph tools (multi-hop queries, risk scoring)
memory_tools.py  memory + action tools (cases, tickets)
agent.py         the agent: Strands + Gemini + system prompt
app.py           Streamlit UI with highlighted graph path
```

## Demo flow

1. Ask *Which vulnerability should we fix first and why?* → see the openssl vs log4j reasoning and the highlighted path.
2. Ask *Open tickets for the public-facing services affected by CVE-2026-1004* → tickets appear in the sidebar, assigned to the owning teams.
3. Reset the conversation and ask *What do we already know about CVE-2026-1004?* → the agent recalls its earlier case and tickets from the graph.

## Limitations and next steps

- The data is synthetic; a real version would ingest SBOMs, scanner output and an ownership directory.
- Tickets are stored in the graph; the next step is pushing them to GitHub Issues or Jira.
- Adding graph algorithms (e.g. PageRank on the dependency graph) and exposing the tools over MCP.
